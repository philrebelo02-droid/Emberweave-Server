# 1. The Pipeline

```text
PROPOSED → ASSIGNED → IN_PROGRESS → IN_REVIEW → APPROVED → MERGED
                ↘ REJECTED ↗              ↘ CHANGES_REQUESTED ↗
```

| State | Meaning | Who moves it |
|---|---|---|
| PROPOSED | Idea recorded, not yet committed | anyone (including her) |
| ASSIGNED | Exactly one owner accepted it (Rule 3) | Phil or the Brain under standing orders |
| IN_PROGRESS | Owner is executing | the owner |
| IN_REVIEW | Work product delivered, awaiting review | the owner marks ready |
| CHANGES_REQUESTED | Review found problems; back to owner | reviewer |
| APPROVED | Review passed AND approval granted | Phil (see approval matrix) |
| MERGED | Change landed in the repo / archive | Claude (write keys) or Phil |
| REJECTED | Dead; reason recorded as a lesson | Phil |
| BLOCKED | Waiting on a dependency; reason recorded | the owner |

# 2. Approval Matrix (what needs whose signature)

| Work type | Reviewer | Approver | Merge authority |
|---|---|---|---|
| Brain code (her own folder) | ChatGPT (reasoning/QA) | Phil | Kimi at Phil's direction |
| Game repo code | ChatGPT | Phil | Claude |
| Architecture decisions | ChatGPT | Phil | — (documented in docs/) |
| Art assets | Grok (visual identity) | Phil | Grok/Claude pipeline |
| Design docs (archive) | Kimi (advisory) or ChatGPT | Phil | Phil |
| World-state / task changes | — (logged) | Brain under standing orders | automatic |

Rule: **no work reaches production without approval.** The workflow is the gate; nothing
skips IN_REVIEW except trivial changes Phil pre-authorizes by class (see §6).

# 3. What Gets Built (Phase A — paper workflow, no git)

1. **Extended task statuses** in memory/tasks.json: the 9 states above. `task: list` shows the
   pipeline position; tasks stuck >7 days in one state get flagged stale in metrics.
2. **Proposal queue** — memory/proposals.jsonl. New command: `task: propose <owner> <priority>
   <what>` — lands as PROPOSED, never auto-assigned. Phil (or standing orders) promotes to
   ASSIGNED.
3. **Review records** — `task: review <id> <verdict> <notes>` writes verdict + notes +
   reviewer + date into the task. Verdicts: approve / changes_requested / reject.
4. **Approval gate, enforced in code** — a task whose work type is protected (see matrix)
   cannot move to MERGED/done without a review record and an approval record. The gate lives
   in complete_task(); bypassing it requires Phil's explicit override command, which is itself
   logged as a decision.
5. **Interface docs rule** (from 4. EMBERWEAVE EXECUTIVE STRUCTURE.md): any task touching
   another department's directory must attach a one-paragraph interface note at IN_REVIEW —
   what changed, what others must do differently. Stored on the task.
6. **Everything logged as decisions** — state transitions already write decision records
   (Step 6); the workflow inherits that for free.

# 4. What Stays Manual (until Step 17, git integration)

- **Courier role:** Phil (or the Brain's reports) carries work products between the specialist
  AIs. The workflow tracks the state; it does not yet transport the artifacts.
- **Review execution:** ChatGPT reviews when Phil pastes the work product to it; the Brain
  records the verdict. Phase B automates the handoff.
- **Merge:** Claude/Phil merge by hand. Phase B (Step 17) adds branches, commit review, and
  change logs — the workflow's MERGED state then triggers on actual git events.

# 5. Rollout
